# SaveStream V2 API contract

`docs/openapi.yaml` is the canonical machine-readable contract for SaveStream V2. This document explains the rollout rules that are easy to miss when reading the schema alone.

## B0 rollout rule

B0 freezes the V2 surface before the implementation phases. Existing V1 endpoint behavior is unchanged.

New V2-only routes are registered by B0 so their `operationId` values can be checked against the frozen contract. Until the owning backend phase lands, those routes return HTTP `501` with the normal error envelope and `error.code = "NOT_IMPLEMENTED"`.

The owning implementation phases are:

- B1: `GET /v1/me/entitlement`, Free/Pro derivation, Watch limits 3/20, Pro cloud concurrency 3, Free manual-trial compatibility, and the first three `auto_record_state` values. **Implemented.**
- B2: cloud-slot waiting, `waiting_for_cloud_slot` / `missed_no_cloud_slot`, and automatic Watch resume after verified purchase credit. **Implemented.**
- B3: devices, push-facing Watch fields, notification kinds/preferences, creator-LIVE notifications, and push delivery. **Implemented.**
- B4: local recording sessions, local metadata sync, rewarded ads, and authoritative local minute counters.
- B5: store product IDs and App Store / Google Play purchase verification.
- B6: `GET /v1/app/status` plus final cloud recording expiry/charge fields.

## Compatibility during rollout

V2 additions to an already-existing response are additive. New properties on `Watch`, `Recording`, `CreditPackage`, `Notification`, and `NotificationPreferences` are intentionally not required by the frozen schema while the phases are rolling out. Clients must tolerate their absence and use the documented defaults until the owning phase is deployed.

No existing field, operation ID, enum member, or error code is removed or renamed by B0.

The existing error envelope remains:

```json
{
  "error": {
    "code": "SOME_CODE",
    "message": "Human-readable text",
    "request_id": "req_...",
    "retryable": false,
    "details": {}
  }
}
```

Clients branch on `error.code`, not on `message`.

## Existing schema names

The V2 handoff uses product-facing names such as “WatchResponse” and “RecordingResponse”. The frozen OpenAPI already calls those schemas `Watch` and `Recording`; B0 extends those existing schemas instead of creating duplicates.

Local-recording creator metadata reuses the existing `Creator` schema:

```json
{
  "platform": "tiktok",
  "username": "linastudio",
  "display_name": "Lina Studio",
  "avatar_url": null
}
```

This replaces the handoff example that used a separate `handle` field.

## Success responses that had no body in the handoff

The V2 handoff specified the action but no success payload for several endpoints. B0 freezes those operations as `204 No Content` so clients do not depend on an invented response body:

- `POST /v1/local-recordings/sessions/{session_id}/extend`
- `POST /v1/local-recordings/sessions/{session_id}/finish`
- `DELETE /v1/local-recordings/{id}`
- `PUT /v1/me/devices/{device_id}`
- `DELETE /v1/me/devices/{device_id}`
- successful `GET /v1/webhooks/admob-ssv`

The AdMob SSV callback verifies the provider-defined signed query string. B0 intentionally does not freeze every provider query parameter; B4 owns the verifier.

## Credits and minutes

The backend ledger continues to store integer credits. One credit equals one minute of cloud recording. V2 cloud-duration fields use minutes (`*_minutes`); clients may display hours and minutes.

Local Free minutes are a separate B4 daily allowance and are not entries in the cloud credit ledger.

## Cloud slot states

V2 adds two recording states:

- `waiting_for_cloud_slot`: a creator is LIVE but the account is already using all cloud slots. This state does not consume a cloud slot.
- `missed_no_cloud_slot`: the LIVE ended before the queued recording obtained a slot. It is terminal and charges zero minutes.

B2 implements the FIFO transition behavior. A waiting row does not reserve credit, does not enqueue a recording worker, and is excluded from the set that consumes a user's three Pro cloud slots. `queue_position` is computed dynamically from `created_at` plus the recording ID, so positions close up when a waiter leaves the queue.

When a cloud slot becomes free, the backend wakes the oldest waiting Watch and forces a fresh LIVE check. Only that fresh check may promote the FIFO head to `queued`; cached `live_status` is never enough. If the LIVE has ended, the waiter becomes `missed_no_cloud_slot`, charges zero minutes, and emits the in-app `recording_missed` notification.

System-wide worker-queue saturation remains the existing `queued` behavior and is separate from the per-user cloud-slot queue. The current deployment capacity noted by the V2 decisions is six simultaneous recording workers; B2 does not raise that global limit. Capacity sizing and the pre-launch increase remain B8 work.

## Local recording boundary

For a local recording, the backend grants a time lease, resolves the source stream and stores metadata. The video bytes remain on the device and are never uploaded through the local-recording API.

A Pro account may have an unlimited local entitlement. In that mode an extension may omit `reward_id`; the backend configuration in B4 decides whether Pro local recording is `unlimited` or `disabled`.

## B5 store purchases

B5 implements one-time in-app credit purchases; there is no subscription state. The canonical catalog is shared by web and mobile:

- Starter — 3,000 credits / 3,000 cloud minutes (50h), USD 9.99, product ID `savestream.hours.50`.
- Standard — 9,000 credits / 9,000 cloud minutes (150h), USD 24.99, product ID `savestream.hours.150`.
- Premium — 24,000 credits / 24,000 cloud minutes (400h), USD 59.99, product ID `savestream.hours.400`.

`POST /v1/billing/store-purchases` never trusts the app to grant credit. The App Store path verifies the StoreKit signed transaction JWS, fetches the same transaction through the App Store Server API, and verifies Apple's server-signed JWS again. The Google Play path looks up the purchase token with the Google Play Developer API, requires purchase state `Purchased`, then acknowledges and consumes the one-time product after the ledger grant. Store credit grants use the store transaction ID as the ledger idempotency key, so replaying the same transaction never grants twice.

The feature is disabled by default with `SAVESTREAM_STORE_PURCHASE_PROVIDER=disabled`; in that state the purchase endpoint fails closed with 503. `fake` is available only outside production for automated tests. `live` enables both real store adapters.

Purchased credit has no expiry field and is consumed only by the normal cloud-credit ledger. The first verified store purchase therefore makes the account Pro under B1, and the existing B2 purchase-grant path immediately resumes Watches paused for insufficient credit.

Refunds are store-driven only. `POST /v1/webhooks/app-store` verifies App Store Server Notifications V2 and accepts a signed `REFUND`. `POST /v1/webhooks/google-play` verifies the authenticated Pub/Sub OIDC token and accepts a one-time-product `voidedPurchaseNotification`. Refund events are idempotent, mark the order `refunded`, and claw back only credit that can be removed without taking posted balance below active reservations or zero. Credit already spent is not turned into a negative debt.

B5 live credentials/configuration:

- Apple: `SAVESTREAM_APP_STORE_BUNDLE_ID`, `...ISSUER_ID`, `...KEY_ID`, `...PRIVATE_KEY[_FILE]`, `...ROOT_CERTIFICATES_JSON[_FILE]` (JSON array of base64 DER Apple roots), `...APP_APPLE_ID`, and `...ENVIRONMENT=sandbox|production`.
- Google: `SAVESTREAM_GOOGLE_PLAY_PACKAGE_NAME`, `...SERVICE_ACCOUNT_JSON[_FILE]`, `...RTDN_AUDIENCE`, and `...RTDN_SERVICE_ACCOUNT_EMAIL`.
- Shared: `SAVESTREAM_STORE_PURCHASE_TIMEOUT_SECONDS`.

No Apple or Google credential is committed. The live adapters are covered with injected signed-data/API doubles for Apple and an in-process HTTP mock plus OIDC double for Google.

Web checkout through the existing Lemon Squeezy payment flow is unchanged.

## B1 entitlement and plan limits

B1 derives Pro from two conditions: the account has at least one order in the paid-order status set used by retention **and** current available cloud credit is greater than zero. Signup/trial credit alone never makes an account Pro. A fully refunded order does not count as a paid purchase.

Watch creation is limited to 3 for Free and 20 for Pro. Existing Free accounts already above 3 Watches keep their rows but cannot create another Watch until they become Pro or drop below the limit. A limit failure uses `WATCH_LIMIT_REACHED` with `details.limit` and `details.plan`.

Automatic cloud recording requires Pro. Creating or updating a Watch with `auto_record=true` while Free returns `PLAN_REQUIRED`. Existing legacy Free rows that already have `auto_record=true` are preserved; the scheduler skips them and their `auto_record_state` is `off`.

For backwards compatibility with the web trial, a Free account that has trial credit may still create one manual cloud recording at a time through `POST /v1/recordings`. Pro accounts may have up to three active cloud recordings. The public entitlement still reports `max_concurrent_cloud_recordings=0` for Free because Mobile Free does not expose cloud recording.

The B1 local entitlement block is intentionally provisional: 10 daily minutes remaining, zero rewards used, and the next UTC reset. B4 replaces those counters with the authoritative daily-minute/reward ledger. Pro reports `local.unlimited=true` in B1 to match the locked product decision; B4 adds the runtime configuration switch.


## B2 purchase resume and failure charging

Verified purchase credit uses the existing billing ledger and then reactivates every Watch for that user whose status is `paused_insufficient_credit`. Reactivation sets the Watch back to `active` and makes it immediately due for the scheduler; it does not create a backfill recording for time already missed. Replaying the same verified payment remains idempotent and does not grant credit twice.

A credit-paused Watch that already owns a `waiting_for_cloud_slot` row keeps that waiter. After purchase, the resumed Watch gets a fresh LIVE check; if it is still LIVE and is the FIFO head, the waiter is promoted. If the LIVE ended first, it becomes `missed_no_cloud_slot`.

The existing failure rule is unchanged: a cloud recording that reaches `failed` releases the whole active reservation and records `actual_cost = 0`. B2 tests this together with slot release so promotion cannot accidentally turn a failed recording into a partial charge.


## B3 devices and push

Device registrations are scoped to both the account and the authenticated session. `PUT /v1/me/devices/{device_id}` upserts the current session binding; `DELETE` is idempotent. Revoking the corresponding auth session (logout, logout-all, explicit session revoke, password reset, refresh-token reuse, or account deletion) removes its device registrations so stale sessions cannot continue receiving push.

`notify_on_live` defaults to `true` on every Watch. It controls only creator-LIVE notifications; turning it off does not stop Watch polling or automatic recording. The global `creator_live` preference defaults to `true`, while `marketing` defaults to `false`. `recording_expiring` and `free_minutes_low` are stored now for B6. Transactional kinds such as purchase completion do not have an opt-out switch.

Creator-LIVE notifications are emitted only on a transition into LIVE (or when the resolved LIVE room changes), not on every scheduler poll. They use `resource_type=watch` and the Watch ID for deep linking. Existing recording notifications, including B2 `recording_missed`, also enter the push pipeline.

Push delivery is asynchronous: notification creation writes an outbox event, Celery dispatches a push task with retry/backoff, and the task sends to all registered devices with a non-null token. An FCM response marking a token `UNREGISTERED` clears that token. Push data includes `notification_id`, `type`, and when applicable `resource_type` / `resource_id`.

Push copy is localized from each device's `locale`; B3 provides English and Vietnamese, with English as the fallback.

External configuration is disabled safely by default:

- `SAVESTREAM_PUSH_PROVIDER=noop` (default) or `fcm`.
- `SAVESTREAM_PUSH_FCM_SERVICE_ACCOUNT_JSON` or its standard `_FILE` form when FCM is enabled.
- `SAVESTREAM_PUSH_FCM_BASE_URL` and `SAVESTREAM_PUSH_FCM_TOKEN_URL` are overrideable for tests; production FCM endpoints must use HTTPS.
- `SAVESTREAM_PUSH_TIMEOUT_SECONDS` controls outbound FCM timeout.

No Firebase credential is committed to the repository, and the B3 tests exercise the real FCM HTTP v1 adapter against an in-process mock transport.


## B6 app status, retention and alerts

`GET /v1/app/status` is public and returns server-controlled minimum supported versions for Android/iOS plus maintenance state and optional ETA. These values live in backend configuration so the minimum version or maintenance flag can change without publishing a new mobile app. D4 later adds database-backed runtime overrides on top of these server defaults.

Cloud retention follows purchase history: accounts with a qualifying paid purchase retain cloud recordings for 30 days; accounts without one retain them for 7 days. `RecordingResponse` includes `expires_at`, `playback_ready`, `engine = "cloud"`, and `minutes_charged` from the settled cloud cost. `playback_ready` is true only when a playable cloud video exists.

B6 runs a periodic retention-notification scan. A recording with a stored artifact receives at most one `recording_expiring` notification when it enters the configured window (24 hours by default). When a cloud recording settlement reduces posted cloud credit to zero, B6 emits one `cloud_minutes_exhausted` notification for that exhaustion. B6 also provides the idempotent `free_minutes_low` primitive and threshold configuration; B4 invokes it when the real local-minute ledger is charged.

Server settings introduced/normalized in B6:

- `SAVESTREAM_APP_MIN_SUPPORTED_ANDROID` and `SAVESTREAM_APP_MIN_SUPPORTED_IOS`.
- `SAVESTREAM_MAINTENANCE_ACTIVE` and optional ISO-8601 `SAVESTREAM_MAINTENANCE_ETA`.
- `SAVESTREAM_RECORDING_RETENTION_DAYS=30` and `SAVESTREAM_RECORDING_RETENTION_DAYS_FREE=7`.
- `SAVESTREAM_RECORDING_EXPIRING_WINDOW_HOURS=24`.
- `SAVESTREAM_FREE_MINUTES_LOW_THRESHOLD=2`.

The locked Pro-local-recording switch remains owned by B4 (`SAVESTREAM_PRO_LOCAL_RECORDING=unlimited|disabled`); B6 does not hardcode that behavior.


## B4 local recording and rewarded ads

Free mobile local recording is metered in a separate daily ledger: 10 minutes per account per UTC day by default. Local sessions are leases; the backend returns a short-lived stream URL and metadata but never records or uploads the local video. Finishing a session charges the Free ledger by recorded seconds rounded up to minutes, capped by the Free portion granted to that lease. Expired leases are closed by a periodic worker after the configured grace window and charge their full granted Free portion.

Rewarded ads use a server-side verification flow. `POST /v1/rewards` creates an intent and returns `ssv_user_id` plus `ssv_custom_data`; only a verified SSV callback changes the reward to `valid`. The production AdMob adapter verifies the raw callback query with ECDSA SHA-256 and cached AdMob public keys. Reward verification is disabled by default; the fake verifier is available only outside production for tests.

A `local_minutes` reward grants 10 minutes by default and is consumed exactly once when starting or extending a local recording lease. Two verified `local_slot` rewards are paired into a time-limited second-slot grant. While that grant is active, `local.max_concurrent_sessions` is 2 and `local.second_slot_expires_at` reports its expiry; otherwise one local slot is available.

The daily cap counts only verified rewards (8 by default). Pending rewards do not count. Consecutive invalid callbacks trigger a temporary server-side reward lock. A valid reward remains usable for the configured validity period, including callbacks that arrive after the app's short polling window.

Pro manual local recording follows the locked server-side switch `SAVESTREAM_PRO_LOCAL_RECORDING=unlimited|disabled`. In `unlimited` mode, Pro leases are long (4 hours by default), do not charge the Free ledger, and can extend without a reward ID. In `disabled` mode the local start/extend path fails with `LOCAL_RECORDING_DISABLED`.

B4 configuration:

- `SAVESTREAM_PRO_LOCAL_RECORDING=unlimited|disabled`.
- `SAVESTREAM_FREE_LOCAL_DAILY_MINUTES=10`.
- `SAVESTREAM_REWARD_PROVIDER=disabled|fake|admob`.
- `SAVESTREAM_REWARD_DAILY_CAP=8`, `SAVESTREAM_REWARD_MINUTES=10`, `SAVESTREAM_REWARD_EXTENSIONS_CAP=4`.
- `SAVESTREAM_LOCAL_UNLIMITED_LEASE_SECONDS=14400`, `SAVESTREAM_LOCAL_LEASE_GRACE_SECONDS=60`.
- `SAVESTREAM_REWARD_VALID_SECONDS=86400`, invalid-lock settings, verifier timeout, and the AdMob public-key URL.
